1. Clientul cere, serverul răspunde

Internetul este infrastructura care conectează rețele și calculatoare. Web-ul este unul dintre serviciile care folosesc această infrastructură: pagini și resurse accesibile prin adrese și legături.

În aplicația noastră, browserul este clientul. El cere programul cinematografului. Serverul primește cererea, o procesează și trimite un răspuns.

  1. 1. PrezentareBrowserul afișează filmele și formularul de rezervare.
  2. 2. LogicăAplicația de pe server verifică dacă locul A2 este liber.
  3. 3. DateBaza de date păstrează filmele, locurile și rezervările.

Acestea sunt trei responsabilități, nu neapărat trei calculatoare. Pentru un site simplu, serverul poate doar să trimită fișiere HTML, CSS și JS, fără o bază de date.

O validare în browser ajută utilizatorul. Pentru o rezervare reală, serverul verifică din nou datele și disponibilitatea: două persoane pot încerca același loc în același timp.

2. URL-ul: adresa și câteva indicații

https://cinema.example/filme?zi=vineri#program
  • https: schema, care indică aici folosirea HTTP printr-o conexiune protejată cu TLS.
  • cinema.example: numele gazdei, adică serverul căruia ne adresăm.
  • /filme: calea resursei.
  • ?zi=vineri: query string, cu un parametru pe care aplicația îl poate folosi pentru filtrare.
  • #program: fragmentul, folosit de browser pentru o secțiune din pagină. Nu este trimis în cererea HTTP.

Uneori apare și portul: în http://localhost:8000, serverul local ascultă pe portul 8000. O cale precum /filme poate fi o rută a aplicației; nu trebuie să fie un fișier cu acel nume pe disc.

Opțional: citim un URL cu JavaScript 
const adresa = new URL("https://cinema.example/filme?zi=vineri#program");
console.log(adresa.hostname);               // "cinema.example"
console.log(adresa.pathname);               // "/filme"
console.log(adresa.searchParams.get("zi")); // "vineri"
console.log(adresa.hash);                   // "#program"

Acest cod doar analizează textul adresei. Nu deschide site-ul și nu trimite o cerere.

3. De la adresă la pagina desenată

  1. Găsește serverul. Dacă are nevoie, browserul folosește DNS pentru a afla adresa IP asociată numelui gazdei. Unele informații sau conexiuni pot fi deja disponibile.
  2. Cere documentul. Prin conexiunea potrivită, trimite o cerere HTTP pentru pagină.
  3. Citește HTML-ul. Construiește DOM-ul și descoperă resurse precum CSS, JavaScript și imagini.
  4. Obține resursele. Unele se descarcă, altele pot fi refolosite din cache. Cererile se pot suprapune; browserul nu le execută obligatoriu una câte una.
  5. Calculează aspectul. Din DOM și regulile CSS construiește informațiile necesare pentru stiluri, dimensiuni și poziții, apoi desenează pagina.
  6. Răspunde la interacțiuni. JavaScript poate modifica DOM-ul sau cere date suplimentare fără să reîncarce toată pagina.

CSSOM este reprezentarea regulilor CSS în browser. Împreună cu DOM-ul, ajută la stabilirea aspectului. O pagină poate folosi și resurse de pe alte servere, de exemplu o imagine sau un videoclip.

Legătura cu lecțiile noastre

<link rel="stylesheet" href="styles.css" />
<script src="script.js" defer></script>

Pentru un script extern obișnuit, defer permite descărcarea în timpul citirii HTML-ului și amână execuția până după parcurgerea documentului. Putem pune scriptul în <head> și găsi elementele paginii când rulează.

Lectură suplimentară: MDN: imaginea de ansamblu a HTTP.

4. HTTP: două mesaje cu roluri diferite

HTTP stabilește cum comunică un client și un server. Poate transporta HTML, imagini, JSON și multe alte tipuri de date. HTTPS protejează comunicarea în tranzit; metoda, headerele și codurile de status păstrează aceleași roluri.

Cererea: „Vreau datele filmului 1”

GET /api/filme/1 HTTP/1.1
Host: cinema.example
Accept: application/json

GET este metoda, /api/filme/1 este ținta cererii, iar liniile următoare sunt headere. Această cerere nu are corp.

Răspunsul: „L-am găsit, acestea sunt datele”

HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"titlu":"Drum spre Marte","pret":20}

200 este codul de status. Content-Type descrie formatul corpului. Linia goală separă headerele de corpul mesajului.

Mesajele sunt simplificate și scrise în forma lizibilă HTTP/1.1. HTTP/2 și HTTP/3 folosesc alte reprezentări pe conexiune, dar păstrează conceptele de metodă, status, headere și corp.

Stateless nu înseamnă că serverul nu poate salva date

HTTP nu leagă automat două cereri de același utilizator. Aplicația poate totuși păstra date în baza de date și poate recunoaște o sesiune printr-un identificator trimis cu cererile.

Detalii: MDN: HTTP stateless și sesiuni.

5. Metoda spune ce vrem să facem

CRUD înseamnă Create, Read, Update, Delete: creare, citire, actualizare și ștergere. Într-un API de rezervări, putem avea următoarea convenție:

Cinci metode întâlnite des
MetodăExempluIntenție
GET/api/filmeCitim lista filmelor.
POST/api/rezervariTrimitem date pentru o rezervare nouă.
PUT/api/rezervari/42Înlocuim reprezentarea rezervării cu cea trimisă.
PATCH/api/rezervari/42Modificăm parțial rezervarea, de exemplu locul.
DELETE/api/rezervari/42Ștergem rezervarea.

Serverul trebuie să implementeze aceste operații. Scrierea lui POST într-un apel nu creează singură o rezervare. Contractul API-ului stabilește adresele, câmpurile și răspunsurile.

POST /api/rezervari HTTP/1.1
Host: cinema.example
Content-Type: application/json

{"filmId":1,"loc":"A2"}

Aici corpul conține datele noii rezervări. GET ar trebui folosit pentru citire, fără să cerem prin el ștergerea sau crearea unei rezervări. POST are și alte utilizări, nu doar crearea de resurse.

De recunoscut: HEAD și OPTIONS

HEAD cere informațiile pe care le-ar oferi GET, dar fără corpul răspunsului. OPTIONS cere informații despre opțiunile de comunicare; îl poți întâlni și la verificările CORS făcute de browser.

Referință: MDN: metode HTTP.

6. Statusul spune cum s-a terminat cererea

Prima cifră indică familia: 1xx informații intermediare, 2xx succes, 3xx redirecționare sau reutilizare condiționată, 4xx probleme legate de cerere și 5xx probleme pe server.

Codurile pe care le urmărim la început
CodCe înțelegemExemplu
200 OKCerere reușită.Am primit lista filmelor.
201 CreatedA fost creată o resursă.Rezervarea nouă are ID-ul 42.
204 No ContentSucces, fără corp de răspuns.Rezervarea a fost ștearsă.
302 FoundRedirecționare temporară.Browserul urmează adresa din Location.
304 Not ModifiedSe poate refolosi copia validată din cache.Resursa nu s-a schimbat; nu primim din nou corpul.
400 Bad RequestServerul consideră cererea incorectă.În API-ul nostru lipsește câmpul loc.
401 UnauthorizedLipsesc credențiale de autentificare valide.Trebuie să ne autentificăm.
403 ForbiddenServerul refuză accesul.Un client nu poate modifica programul cinematografului.
404 Not FoundResursa nu a fost găsită.Nu există filmul cu ID-ul 999.
500 Internal Server ErrorEroare neașteptată pe server.Aplicația nu a putut termina operația.

Un 4xx nu înseamnă obligatoriu că utilizatorul a greșit: poate fi și un link vechi. La 5xx, interfața poate afișa un mesaj și permite reîncercarea, dar repararea cauzei ține de server. Dacă rețeaua nu funcționează, este posibil să nu primim deloc un status HTTP.

Host: cinema.example
Accept: application/json

Răspuns → browser

HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"titlu":"Drum spre Marte","pret":20}

200 OK: filmul a fost găsit. Corpul răspunsului conține date JSON.

7. Headerele descriu mesajul și contextul lui

Un header are forma Nume: valoare. Numele nu ține cont de litere mari sau mici: Content-Type și content-type desemnează același header.

Ce citim în panoul Network
HeaderUnde îl întâlnimRol
HostCerere HTTP/1.1Gazda și, când este cazul, portul.
AcceptCerereTipuri de conținut acceptate, de exemplu application/json.
Content-TypeCerere sau răspuns cu corpFormatul corpului trimis, de exemplu text/html.
AuthorizationCerereCredențiale pentru autentificare, de exemplu un token Bearer.
CookieCerereCookies eligibile pentru acea cerere.
Set-CookieRăspunsIndică browserului să creeze sau să actualizeze un cookie.
LocationRăspunsAdresa unei redirecționări sau a resursei nou create.
Cache-ControlCerere sau răspunsDirective despre folosirea cache-ului.

Accept: application/json înseamnă „pot primi JSON”. Content-Type: application/json înseamnă „corpul acestui mesaj este JSON”. Sunt informații diferite.

Opțional: alte nume din material
  • Accept-Language: preferințe de limbă; Accept-Encoding: compresii acceptate.
  • User-Agent: informații declarate de client despre software-ul folosit.
  • Referer: informații despre pagina de proveniență, în limitele politicii de confidențialitate aplicate. Numele headerului este chiar „Referer”.
  • Content-Length: lungimea corpului în octeți, când este specificată; Content-Encoding: codificarea aplicată, de exemplu gzip.
  • Last-Modified: data ultimei modificări; poate fi folosit pentru validarea unei copii din cache.

Browserul gestionează singur multe headere, inclusiv Host și Cookie. Nu le copiem pe toate într-un apel fetch().

8. Cookies: date mici, trimise când se potrivesc regulile

Un cookie este o pereche nume–valoare păstrată de browser, împreună cu reguli despre durată și trimitere. Poate ajuta la sesiuni, preferințe sau urmărirea activității.

Serverul îl setează; browserul îl trimite ulterior

Set-Cookie: sesiune=id-demonstrativ; Path=/; Secure; HttpOnly; SameSite=Lax

La o cerere ulterioară eligibilă către acel site, browserul poate trimite:

Cookie: sesiune=id-demonstrativ

Nu trimite toate cookies către orice site. Contează gazda, calea, HTTPS, regulile SameSite și politicile browserului. Atributele precum Path nu se repetă în headerul Cookie.

  • Secure: limitează trimiterea la conexiuni HTTPS, cu excepții locale definite de browser.
  • HttpOnly: împiedică accesul prin JavaScript, de exemplu prin document.cookie. Se setează de server.
  • SameSite: controlează trimiterea în contexte între site-uri.
  • Max-Age sau Expires: stabilesc durata. Fără ele, cookie-ul este de sesiune; restaurarea sesiunii browserului îl poate păstra.

HttpOnly nu garantează că o valoare este autentică și nu înlocuiește validarea pe server. Într-o sesiune obișnuită trimitem un identificator greu de ghicit, nu parola utilizatorului.

Detalii: MDN: folosirea cookies.

Opțional: Domain, Path și un cookie de preferință

Fără Domain, cookie-ul este limitat la gazda care l-a setat. Specificarea unui domeniu permis poate include și subdomeniile. Path=/cont se potrivește cu /cont și /cont/bilete, dar nu cu /contact. Fără Path explicit, browserul calculează o cale implicită din adresa cererii.

Path controlează trimiterea; nu este o barieră de securitate între paginile aceluiași site.

// Rulează pe serverul local. Este doar o preferință demonstrativă.
document.cookie = "preferintaCinema=ro; Max-Age=3600; Path=/; SameSite=Lax";
console.log(document.cookie); // Cookies accesibile JavaScript, fără cele HttpOnly.

// Ștergem același cookie folosind același nume și aceeași cale.
document.cookie = "preferintaCinema=; Max-Age=0; Path=/; SameSite=Lax";

Cookie-ul de preferință este accesibil JavaScript; exemplul nu creează o autentificare.

Referință: MDN: atributele Set-Cookie.

9. Sesiunea leagă cererile de același context

Într-o implementare obișnuită, serverul păstrează datele sesiunii, iar browserul păstrează într-un cookie identificatorul ei.

  1. Mara trimite formularul de autentificare prin HTTPS.
  2. Serverul verifică datele, creează o sesiune și trimite identificatorul prin Set-Cookie.
  3. La cererea pentru „Biletele mele”, browserul trimite cookie-ul eligibil.
  4. Serverul validează sesiunea și verifică ce bilete are voie Mara să vadă.
  5. La deconectare, serverul invalidează sesiunea și cere eliminarea cookie-ului.

Poate exista și o sesiune anonimă, de exemplu pentru un coș înainte de autentificare. O sesiune a aplicației nu este același lucru cu sessionStorage.

Autentificare și autorizare: două întrebări

  • Autentificare: „Cine ești?” Verificăm identitatea Marei.
  • Autorizare: „Ce ai voie să faci?” Mara poate vedea biletele ei; administratorul poate modifica programul.

Un utilizator autentificat poate primi 403 când încearcă o operație interzisă. Ascunderea unui buton în HTML nu protejează operația: serverul verifică drepturile pentru fiecare cerere relevantă.

De recunoscut: Authorization
Authorization: Bearer token-demonstrativ

Unele API-uri folosesc un token în acest header în locul unui cookie de sesiune. Numele headerului nu înseamnă că drepturile sunt acordate automat; serverul verifică tokenul și permisiunile.

10. Când vrem doar să păstrăm o preferință în browser

localStorage și sessionStorage păstrează perechi cheie–valoare ca texte. Nu sunt trimise automat cu cererile HTTP.

Unde păstrăm informația?
MecanismDurată și delimitareExemplu
CookieDupă atribute și politicile browserului; trimis la cererile eligibile.Identificator de sesiune.
localStoragePe origine; persistă între vizite până la ștergere.Preferința pentru genul de film.
sessionStoragePe origine și tab; rezistă la reload, în mod normal se elimină la închiderea tabului.Un pas temporar al unui formular.

O origine este combinația dintre schemă, gazdă și port. http://localhost:8000 și http://localhost:5500 au spații de stocare diferite.

localStorage.setItem("cinema-gen-preferat", "comedie");
console.log(localStorage.getItem("cinema-gen-preferat")); // "comedie"

localStorage.removeItem("cinema-gen-preferat");
console.log(localStorage.getItem("cinema-gen-preferat")); // null

Pentru a observa persistența după reload, rulează primele două linii, reîncarcă pagina și citește din nou valoarea. Rulează ștergerea separat. Aceleași metode există și pe sessionStorage.

Stocarea poate fi blocată sau ștearsă de utilizator ori de browser. Pentru date esențiale, aplicația trebuie să poată trata această situație. Nu păstrăm parole în Web Storage.

Detalii: MDN: Web Storage.

11. API și JSON: cerem date pentru interfața noastră

Un API este o interfață prin care programele pot folosi funcționalități sau date. Într-un API HTTP, un endpoint este o adresă prin care accesăm o operație sau o resursă, de exemplu GET /api/filme.

JSON este un format text pentru date. Cheile și textele au ghilimele duble. Nu scriem comentarii sau funcții în JSON.

[
  { "id": 1, "titlu": "Drum spre Marte", "pret": 20 },
  { "id": 2, "titlu": "Pisica regizor", "pret": 15 },
  { "id": 3, "titlu": "Pauză de râs", "pret": 25 }
]

Am pus aceste date în exemple-web/filme.json. Le cerem prin HTTP ca pe răspunsul unui API, dar sursa este un fișier static: nu avem încă operații de creare sau ștergere pe server.

Pregătire: deschide pagina prin HTTP

Folosește serverul local pe care îl ai deja pentru curs, de exemplu Live Server în VS Code. Deschide folderul proiectului, apoi lecția prin acel server.

Alternativă: server local cu Python, dacă este instalat

Din terminal, în folderul principal al proiectului, rulează:

python3 -m http.server 8000 --bind 127.0.0.1 --directory html

Deschide http://localhost:8000/Web-Concepts-Dive-Deeper.html. Oprești serverul cu Ctrl + C în terminal. Comanda de mai sus servește doar folderul html.

La deschiderea directă prin file://, browserul poate bloca fetch pentru fișiere locale. Serverul local oferă cereri și răspunsuri HTTP pe care le putem inspecta în Network.

Mai întâi, un exemplu scurt pentru consolă

async function citesteFilmele() {
  try {
    const raspuns = await fetch("exemple-web/filme.json");
    if (!raspuns.ok) {
      throw new Error(`HTTP ${raspuns.status}`);
    }
    const filme = await raspuns.json();
    console.log(filme[0].titlu); // "Drum spre Marte"
  } catch (eroare) {
    console.log(`Încărcarea a eșuat: ${eroare.message}`);
  }
}

citesteFilmele();
  1. fetch() trimite implicit o cerere GET și întoarce o promisiune.
  2. await ne dă obiectul Response. status este codul numeric; ok este true pentru coduri de la 200 la 299.
  3. await raspuns.json() citește și transformă corpul JSON în valori JavaScript.
  4. catch tratează erorile de rețea, eroarea aruncată de noi pentru status și eventualele erori de parsare JSON.

Un răspuns 404 sau 500 nu respinge singur promisiunea fetch. Verificăm raspuns.ok. Pentru un 204, nu apelăm json(): nu există corp de parsat.

Încarcă programul cinematografului

Deschide Network înainte de click ca să vezi cererea reală. Al doilea scenariu cere intenționat un fișier care nu există; pe serverul static local acesta produce 404.

Lista nu a fost încărcată.

    Vezi codul complet al demonstrației fetch

    Scriptul folosește ID-urile din demonstrație. Golește lista la început, verifică răspunsul și creează fiecare rând cu textContent. În finally reactivează controalele.

    const butonIncarca = document.getElementById("incarca-filme");
const sursaFilme = document.getElementById("sursa-filme");
const stareFilme = document.getElementById("stare-filme");
const listaFilme = document.getElementById("lista-filme");

async function incarcaFilme() {
  listaFilme.replaceChildren();

  if (window.location.protocol === "file:") {
    stareFilme.textContent = "Deschide lecția printr-un server local (http://localhost…), apoi încearcă din nou. Vezi pașii de mai sus.";
    return;
  }

  butonIncarca.disabled = true;
  sursaFilme.disabled = true;
  stareFilme.textContent = "Se încarcă filmele…";

  try {
    const raspuns = await fetch(sursaFilme.value);
    if (!raspuns.ok) {
      throw new Error(`HTTP ${raspuns.status}: lista nu a putut fi încărcată.`);
    }

    const filme = await raspuns.json();
    for (const film of filme) {
      const element = document.createElement("li");
      element.textContent = `${film.titlu}: ${film.pret} lei`;
      listaFilme.append(element);
    }
    stareFilme.textContent = `HTTP ${raspuns.status}: ${filme.length} filme încărcate.`;
  } catch (eroare) {
    stareFilme.textContent = `Nu am putut afișa filmele. ${eroare.message}`;
  } finally {
    butonIncarca.disabled = false;
    sursaFilme.disabled = false;
  }
}

butonIncarca.addEventListener("click", incarcaFilme);

    12. Atelier: găsim dovezile în browser

    Network: urmărim cererile

    1. Deschide DevTools → Network, apoi reîncarcă lecția deschisă prin serverul local.
    2. Alege documentul HTML. În Headers, caută Request URL, Request Method, Status Code și Content-Type.
    3. Observă cererile pentru CSS și JavaScript. În Timing sau Waterfall vezi când au avut loc.
    4. Apasă „Încarcă filmele” și caută filme.json, eventual cu filtrul Fetch/XHR.
    5. În Response sau Preview, verifică lista. Alege apoi fișierul inexistent și compară statusul și corpul.

    Răspunsul 404 al unui server static poate conține HTML, nu JSON. De aceea verificăm statusul înainte să încercăm parsarea. Pentru a urmări o descărcare nouă, poți bifa temporar „Disable cache” cât timp DevTools este deschis.

    Application / Storage: urmărim ce rămâne în browser

    În Chrome, caută Application; alte browsere pot folosi numele Storage. Inspectează Cookies, Local Storage și Session Storage pentru originea locală. Rulează exemplul de preferință din secțiunea 10, citește valoarea după reload, apoi șterge doar cheia creată în exercițiu.

    Instrumente precum Postman sau Fiddler pot ajuta la inspectarea cererilor. Pentru această lecție, DevTools este suficient.

    Recapitulare: cinci întrebări cu răspunsuri
    1. Este 404 o lipsă totală de răspuns? Nu. Serverul a răspuns că resursa nu a fost găsită.
    2. Trimite localStorage automat date spre server? Nu. Scriptul ar trebui să le trimită explicit.
    3. Înseamnă autentificat și administrator? Nu. Drepturile sunt verificate separat.
    4. GET și POST sunt doar două nume pentru aceeași operație? Nu. Exprimă intenții diferite, implementate de server.
    5. Intră fetch automat în catch la 500? Nu. Verificăm statusul sau ok și tratăm eroarea.

    Temă simplă: detectiv în Network

    Deschide această lecție pe serverul local și notează rezultatele într-un fișier tema-web-1.txt.

    1. Reîncarcă pagina cu Network deschis. Notează metoda, statusul și Content-Type pentru documentul HTML și pentru un fișier CSS.
    2. Încarcă lista de filme. Notează aceleași informații pentru filme.json și titlul primului film din răspuns.
    3. Cere fișierul inexistent. Notează statusul și tipul corpului primit: JSON, HTML sau alt format.
    4. Explică în câte o propoziție diferența dintre Accept și Content-Type, respectiv dintre 401 și 403.
    5. Din simulator, alege crearea unei rezervări și identifică metoda, corpul cererii și adresa din Location.

    Nu confunda cererea documentului HTML cu cererea pornită de buton. Folosește filtrul din Network și deschide fiecare rând separat. Simulatorul nu creează rânduri noi în Network.
